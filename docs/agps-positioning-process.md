# A-GPS 辅助定位全过程：网络如何帮助手机更快获得 GNSS fix

> 面向本项目 GSS7000 + CMW500 + Android 的原理学习文档。**A-GPS（Assisted GPS）并不是基站代替卫星定位**。它主要利用网络提供时间、位置、星历或其他辅助信息，帮助接收机更快捕获、解码或解算；具体机制由手机芯片、系统、运营商和协议决定。

## 1. GPS 与 A-GPS 的根本区别

GPS 自主定位需要手机从卫星 RF 信号获取测距与导航信息；A-GPS 则可以提前从网络获得部分原本要通过卫星电文慢慢获取的信息，或者把测量结果交由服务器辅助解算。**A-GPS 通常仍需要 GNSS 测量**，但某些系统也会同时提供蜂窝/Wi-Fi 定位结果；后者不是 GPS fix，测试时必须区分。

| 项目 | 自主 GPS | A-GPS |
| --- | --- | --- |
| 是否必须插 SIM 卡 | 否 | 不一定；取决于辅助数据的获取途径 |
| 是否必须能上互联网 | 否 | 某些模式需要 IP 网络；也可能通过运营商控制面获得 |
| 卫星 RF 信号 | 常规自主定位必需 | 常见 A-GPS 模式仍需要 |
| 时间/位置/星历来源 | 本地缓存或卫星广播 | 可增加网络提供的辅助信息 |
| 定位计算位置 | 主要在终端 | 终端侧或网络辅助/网络侧 |
| 优势 | 独立于蜂窝网络 | 缩小搜索范围、减少等待星历时间、提升弱信号首次定位机会 |
| 风险 | 弱信号下收星历慢 | 依赖网络、协议、服务器、缓存有效期与时间一致性 |

## 2. 辅助信息究竟是什么

1. **粗略时间**：帮助确定卫星信号的码相位/导航数据时间，缩小搜索范围；精度与可信度有区别。
2. **粗略位置**：基站位置、上次位置、网络位置等可帮助预测可见卫星及多普勒；**不是最终 GNSS 精确坐标**。
3. **星历 Ephemeris**：较精确的卫星轨道与时钟参数，可避免在弱信号下等待完整导航电文；必须匹配卫星和有效时间。
4. **历书 Almanac**：粗略星座轨道信息，辅助卫星搜索与可见性预测，不能替代精密星历。
5. **频率/时间参考**：蜂窝网络及其他来源可能提供频率和时间约束，具体精度由实现决定。
6. **差分/完整性等信息**：某些服务还提供误差修正或质量信息；不要把所有网络 GNSS 服务都混称为传统 A-GPS。

## 3. 一次 A-GPS 定位从头到尾发生了什么

### 第 0 步：手机决定要定位

App 请求位置 → Android 定位框架 → GNSS 芯片/厂商 HAL。系统判断缓存的时间、位置、星历是否仍可信，是否需要请求辅助数据。手机设置中的“定位开关”并不等于一定启用了 A-GPS，也不代表一定实际下载成功。

### 第 1 步：手机取得网络连接

可能是蜂窝数据、Wi-Fi、运营商控制面或其他受支持的链路。**SIM 卡本身不携带当前卫星星历**，插卡只可能改变注册、网络时间、数据连接、运营商辅助服务等条件。

若使用 CMW500：手机注册 LTE 小区仅证明**无线接入/注册成功**，不代表已经有 IP 承载、DNS、互联网、SUPL 服务器或 LPP 辅助消息。

### 第 2 步：获取初始时间和粗位置

系统可利用蜂窝网络时间、基站相关信息、上次定位、网络定位等提供初值。粗时间和粗位置让接收机更容易预测卫星可见性与多普勒，减少盲搜索；实际来源和精度取决于平台。

### 第 3 步：请求并接收辅助数据

常见路线包括：

**用户面 SUPL（Secure User Plane Location）**：
- 手机建立 IP 数据连接，与受支持的 SUPL Location Platform 交互。
- 服务器/终端按协商协议交换能力、位置和 GNSS 辅助数据。
- 可能承载星历、时间、粗位置或其他辅助信息；不保证每次 SUPL 会话都传输全部种类。
- 需要正确的 DNS、路由、服务器可达性、TLS/证书和设备配置；实际 SUPL 地址由系统/厂商/运营商决定。

**蜂窝控制面定位（如 LTE LPP）**：
- 终端与网络通过相关信令交换定位能力、辅助数据和测量请求/结果。
- 通常涉及 LTE 核心网定位架构及定位服务器（例如 E-SMLC）等，不是“LTE 小区能注册”就自动存在。
- 具体是否支持取决于 CMW500 配置、许可证、网络侧组件和手机实现。

**预测/扩展星历（XTRA/PSDS 等厂商实现）**：
- 手机可能通过厂商服务下载预测卫星数据并缓存，供之后的 GNSS 启动使用。
- 这与一次实时 SUPL/LPP 会话不同；需用网络日志、GNSS 调试日志和缓存状态证明实际发生。

### 第 4 步：辅助信息进入 GNSS 引擎

系统或厂商 GNSS 栈校验辅助数据的时间、卫星身份、有效期和格式，并交给 GNSS 引擎使用。若数据过期或与 GSS7000 模拟的 UTC/卫星状态不一致，可能**不被采用，甚至干扰首次捕获策略**。不能假设手机“拿到网络就一定使用辅助数据”。

### 第 5 步：GNSS RF 捕获、跟踪和测距

接收机仍然接收 GSS7000 的模拟 GPS 信号，完成相关捕获、跟踪、码相位/伪距测量。辅助时间、位置、星历可减少部分搜索或解码等待，但**不能弥补完全不存在的 RF 信号**。

### 第 6 步：终端或服务器解算

- **MS-Based / UE-Based**：网络提供辅助数据，手机侧使用 GNSS 测量解算位置。
- **MS-Assisted / UE-Assisted**：手机提供 GNSS 测量，服务器可参与位置计算。
- 不同规范和实现的术语有所差别，测试时要记录实际工作模式，不能单凭 Android 定位回调判断。

### 第 7 步：返回位置、记录 TTFF

Android 返回位置结果；同时可记录 GNSS 卫星状态、C/N0、used-in-fix、原始测量及网络辅助会话证据。**融合定位输出**可能先于真正 GNSS fix；本项目的 TTFF 不能把蜂窝/Wi-Fi 粗定位误算为卫星首次定位。

## 4. 为什么 A-GPS 对弱信号尤其重要

自主 GPS 可能需要从极弱的卫星信号中解码低速导航电文，尤其获取有效星历。A-GPS 可通过网络提前提供星历、时间和初始位置，缩短“等导航数据”的时间，并减少捕获搜索范围。但定位是否成功仍取决于 RF 可测量性、卫星几何、接收机算法、辅助数据有效性和测试起点。

**重要：**“室外插卡能定位、箱内没卡不能定位”不能直接证明 A-GPS 缺失是唯一原因，因为 GNSS 信号强度、屏蔽、星座、模拟时间、缓存和网络同时发生了变化。必须控制变量。

## 5. GSS7000 + CMW500 是否能模拟 A-GPS？

**能搭建部分条件，但 LTE 注册不等于完整 A-GPS。**

| 设备/系统 | 能做什么 | 不能据此推断 |
| --- | --- | --- |
| GSS7000 | 模拟 GNSS 卫星 RF、导航数据、固定位置、时间及功率 | 不负责自动向手机提供蜂窝 SUPL/LPP |
| CMW500 | 模拟 LTE 小区、让测试卡手机注册；能力取决于配置/选件 | 注册成功 ≠ IP 上网 ≠ SUPL/LPP 已工作 |
| 测试 SIM | 允许设备接入相应测试网络 | SIM 存在 ≠ 辅助星历已注入 |
| Windows 上位机 | 控制仪表、ADB、采集网络与 GNSS 证据 | 不能只凭 `usedInFix` 判断 A-GPS 是否启用 |
| 辅助服务器/网络 | 按协议提供辅助数据（若已配置） | 不是所有 Android 机型都接受任意自建服务器 |

### 三个递进的现场实验层次

**层次 A：GNSS-only 基线（当前可先做）**
- 手机不使用蜂窝数据/Wi-Fi 辅助，固定 GSS7000 场景与 RF 功率。
- 记录冷/温/热启动定义、TTFF、有效率和导航数据解码行为。
- 注意：关闭网络不一定清除手机已经缓存的预测星历或其他辅助数据。

**层次 B：有网络但不宣称完成 A-GPS（CMW500 LTE）**
- CMW500 建立小区，手机用测试 SIM 注册；核对时间来源、数据承载和 IP 连通性。
- 若没有 SUPL/PSDS/LPP 实际证据，只能标记“LTE 网络可用/已注册”，不能写“A-GPS 已启用”。

**层次 C：真正可核验的 A-GPS**
- 确定目标手机支持的辅助通道（SUPL、LPP、PSDS/XTRA 等）。
- 建立相应服务器/网络侧能力；确认与 GSS7000 的模拟 UTC、位置和卫星星历相容。
- 通过网络抓包、设备 GNSS/系统日志、协议信令和缓存变化证明辅助数据确实送达且被接受（是否被 GNSS 引擎使用还需进一步证据）。
- 在相同 GNSS 场景、功率、手机姿态和清缓存规则下，与 GNSS-only 比较 TTFF/有效率。

## 6. 测试设计：避免把辅助定位效果测错

| 变量 | 必须固定/记录 |
| --- | --- |
| 场景 | GSS7000 场景文件、哈希、WGS84 参考位置、UTC、星历 |
| RF | 仪表功率、校准参考平面、衰减器、天线耦合、手机姿态 |
| 手机 | 型号、固件、GNSS 芯片、是否 Root、定位模式 |
| 网络 | SIM、LTE 注册、IP、DNS、SUPL/PSDS/LPP 证据 |
| 启动 | Cold/Warm/Hot 的实际清除范围、预热/缓存、观察时间 |
| 结果 | 真正 GNSS fix、TTFF、误差、C/N0、used-in-fix、INVALID 原因 |

建议至少对比三组：**无可用网络**、**LTE 已注册但未验证辅助数据**、**已验证辅助数据到达并被接受**。不要把第三组与第一组的差异直接归因于星历，除非其他变量一致。

## 7. 常见误区

- **“没 SIM 卡就不能 GPS 定位”**：错误；自主 GPS 无需 SIM。
- **“CMW500 LTE 注册成功就是 A-GPS 成功”**：错误；还需具体辅助数据传输/使用证据。
- **“A-GPS 是基站计算 GPS 坐标”**：不完整；常见 MS-Based 是手机自己解算。
- **“有星历就不需要卫星信号”**：错误；GNSS 测距仍需要实际 RF。
- **“热启动就是 A-GPS”**：错误；热启动可只依赖本地缓存。
- **“插卡后 TTFF 变快就证明用了 SUPL”**：错误；也可能是网络时间、PSDS、缓存或测试条件变化。
- **“预热几秒不影响正式 HOT TTFF”**：错误；预热可能改变缓存和捕获状态，必须单独定义并报告。

## 8. 与本项目下一步方案的关系

先回答四个证据问题，再决定是否做 CMW500 A-GPS 自动化：
1. 目标手机实际支持哪些辅助协议？能否从日志中看到 SUPL/PSDS/LPP？
2. CMW500 现场是否仅完成 LTE 注册，还是已经具备 IP 数据通路和定位服务器能力？
3. GSS7000 场景的 UTC、星历、位置是否能与辅助数据来源一致？
4. 当前 INVALID/弱信号失败主要来自 GNSS RF、卫星回调时序、星历缺失，还是网络辅助缺失？
