# GPS 自主定位全过程：从卫星信号到手机坐标

> 面向本项目 GSS7000 + Android 手机 + 屏蔽箱的工程学习文档。本文聚焦 **GPS（Global Positioning System）**，不把 GPS 与 GNSS（GPS、北斗、Galileo 等系统的统称）混用。现代手机通常多星座融合，单 GPS 测试需确认设备实际使用的星座。

## 1. 一句话理解 GPS 定位

GPS 接收机通过测量**卫星信号从发射到接收的传播时间**得到多个伪距，结合导航电文提供的卫星轨道、卫星时钟等信息，求解接收机的三维位置与接收机时钟偏差。**不需要 SIM 卡、基站或互联网**也能自主定位；但首次获取时间、弱信号表现会受影响。

关键区分：
- **卫星可见（in view）**：几何上可能在地平线上方；不保证接收到信号。
- **捕获/跟踪（acquired/tracked）**：接收机找到并持续跟踪信号；不保证导航电文已解码或能定位。
- **参与解算（used in fix）**：接收机将某些测量纳入位置解算；Android `GnssStatus.usedInFix` 是回调时刻的状态，不一定严格等同于首次 fix 的卫星集合。
- **首次定位（first fix）**：定位引擎首次输出满足其内部条件的位置。Android 回调还可能包含缓存、融合或非 GNSS 位置，测试时必须检查来源与时间戳。

## 2. 卫星发射的是什么

GPS 卫星发射载波、扩频测距码和导航数据。以常见的 **GPS L1 C/A** 为例：
- L1 载波中心频率约 **1575.42 MHz**。
- C/A 测距码让接收机通过相关运算识别卫星 PRN、测量码相位。
- 传统 GPS LNAV 导航电文包含卫星时钟参数、星历、历书、健康状态及时间等信息。
- GPS 时间与 UTC 不是完全相同的时间尺度；必须正确处理两者偏移，不能直接把手机墙上时钟当作精确 GPS 时间。

**星历（ephemeris）**：某颗卫星的精确轨道与钟差参数，适合较短有效时间窗口，决定能否精确计算卫星在发射时刻的位置。

**历书（almanac）**：覆盖星座的粗略轨道/状态信息，有效时间较长，主要帮助预测哪些卫星可能可见和加快搜索；**历书不能替代精密星历做高精度定位**。

## 3. 接收机从启动到定位的完整链路

### 第 0 步：建立初始状态

接收机可能保存上次的位置、时间、星历、历书、频率误差和辅助数据。状态决定冷/温/热启动的搜索成本。

| 启动类型 | 通常具有的信息 | 典型表现 |
| --- | --- | --- |
| 冷启动 Cold | 缺少可信时间、位置、有效星历 | 搜索空间大，通常需要收集更多导航数据 |
| 温启动 Warm | 有粗时间/位置或历书，但缺少有效星历 | 搜索较快，仍可能需要获取星历 |
| 热启动 Hot | 有较可信时间、位置、有效星历 | 可以较快捕获并定位 |

> 不同芯片、Android 实现和测试规范对 Cold/Warm/Hot 的清除范围不同。**仅关闭再打开定位服务不等于严格冷启动**，也不能只凭 TTFF 长短倒推启动类型。

### 第 1 步：射频接收与数字化

天线接收极弱的卫星信号 → LNA 放大 → 滤波/下变频 → ADC 采样 → 数字基带。灵敏度受天线效率、线损、干扰、噪声系数、射频前端和相关积累能力共同影响。

### 第 2 步：搜索与捕获

接收机针对候选 PRN，在**码相位 × 多普勒频率**二维空间搜索相关峰。相关峰足够可靠时，得到粗码相位和载波频偏。已知大致时间/位置/星历可缩小候选卫星和多普勒搜索范围；完全未知时搜索量更大。

### 第 3 步：跟踪

DLL/PLL/FLL 等跟踪环路持续估计码相位、载波相位/频率和信号质量。接收机可以报告 C/N0，但 **C/N0 高不必然等于参与解算**：还要看跟踪稳定、数据有效、几何和质量控制。

### 第 4 步：位同步、帧同步、导航数据解码

接收机解调导航电文，获得卫星时钟修正、星历、健康状态、时间参数等。传统 GPS L1 C/A LNAV 速率 **50 bit/s**，一帧 **30 秒**，包含 5 个 6 秒子帧；星历主要分布在子帧 1–3，连续正确接收通常需要**约 18–30 秒量级**，但实际时间取决于进入帧的位置、数据丢失、已有缓存及接收机策略。**不能断言所有冷启动必须固定等 30 秒**。

### 第 5 步：构建伪距与卫星位置

接收机结合发射时间与接收时间估计传播时间，计算伪距。伪距不是几何真距离，包含接收机钟差、卫星钟差、大气传播延迟、多径与测量噪声等。

近似测量方程：

\[
\rho_i = \|\mathbf r-\mathbf s_i\| + c(\delta t_r-\delta t_{s_i}) + I_i + T_i + \epsilon_i
\]

其中 \(\mathbf r\) 是待求接收机位置，\(\mathbf s_i\) 是由星历计算的卫星位置，\(c\) 为光速，\(\delta t_r\) 为接收机钟差，\(\delta t_{s_i}\) 为卫星钟差，\(I_i,T_i\) 分别表示电离层和对流层误差。

### 第 6 步：位置、时间与速度解算

单频、单历元的常规三维伪距定位一般至少需要 **4 颗几何条件合适的卫星**，求解 x/y/z 和接收机钟差。若有已知高度、外部时间或其他约束，情况可以不同。使用更多卫星通常有助于冗余和质量控制，但几何分布（DOP）、误差和异常值比单纯数量更重要。速度可由多普勒/连续位置估计。

### 第 7 步：输出位置与质量信息

GNSS 芯片/系统定位栈将结果提供给 Android，App 收到位置回调与卫星状态回调。**这两类回调不保证同时到达**；GNSS 状态的 `usedInFix` 与位置回调需要按单调时钟关联，并保留时间偏差与关联策略，不能伪称完全同步。

## 4. TTFF 到底测什么

**TTFF（Time To First Fix）**是从约定的测试起点到首次满足要求的有效定位之间的时间。测试必须明确：
- 起点：引擎真正启动/开始捕获，还是 App 发送请求的时刻？
- 终点：芯片 GNSS fix、Android GNSS 位置回调，还是融合定位回调？
- 是否允许缓存位置、预热、A-GPS、网络和先前星历？
- 是否检查水平误差、有效时间戳、卫星关联和 fix 来源？

本项目应分别保存：`attempt_start`、`first_fix`、`satellite_status` 的**单调时钟**时间，另记录主机/手机时钟偏移；上位机和手机墙上时钟不一致时，不能直接相减求 TTFF。

## 5. 为什么弱信号会影响定位

随着接收功率降低，捕获所需积累时间可能变长，跟踪更容易失锁，导航电文误码增加，星历无法及时解码，伪距误差变大。手机显示 **20 多 dB-Hz** 是 C/N0，不是 RF 端口功率 dBm；两者不能简单用固定数值互换。

失败可能发生在不同阶段：

| 现象 | 优先排查 |
| --- | --- |
| 看不到卫星 | RF 输出、星座/频点、场景运行、接线/衰减、干扰 |
| 可见但不跟踪 | C/N0、捕获/跟踪门限、频率误差 |
| 跟踪但长期不定位 | 星历/导航电文、时间、卫星健康、几何、测量质量 |
| 已有 fix 但 used-in-fix 为 0 | Android 状态回调时序、卫星身份、关联窗口、厂商实现 |
| 室外能定位而箱内不能 | GNSS 信号与辅助条件同时变化，需分别控制变量 |

## 6. GSS7000 静态场景如何对应 GPS 链路

GSS7000 负责模拟卫星信号及其导航数据，**不是给手机直接下发定位坐标**。静态场景中接收机参考位置固定，卫星运动、传播时延、多普勒和导航电文仍随场景时间变化。手机必须从 RF 信号中完成捕获、跟踪和位置解算。

本项目建议的基础实验：
1. 确认静态场景的 WGS84 位置、UTC、星历、星座和 RF 参考平面。
2. 在强且安全的基准信号下先验证 GPS_ONLY 的冷/温/热启动定义与有效定位。
3. 固定手机姿态、场景、温度、USB、LTE 条件，再按批准范围逐档降低功率。
4. 每档记录至少：有效尝试次数、TTFF、定位误差、每星 C/N0、卫星身份与 used-in-fix、失败原因。
5. 将 **无定位 FAIL**、**证据不完整 INVALID**、**仪表/USB 中断** 分开统计，不能混为一谈。

静态场景菜单与加载步骤见 [GSS7000 静态场景文档](gss7000-static-scenario.md)；射频校准见 [硬件文档](hardware.md)。
